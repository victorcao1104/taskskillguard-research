## Extraction scope and novelty

There are 48 fixtures in 24 construction families, two fixtures per family, with 16 fixtures and eight whole families in each split. No family crosses splits. These are prospective bounded-coverage stress tests, not an estimate of operation frequency in real repositories. Operations and elementary syntax are deliberately shared between some families; split separation is at the listed construction-family level, not at entire language or API level.

The Phase4 families inspected included curl, shell file operations and stream pipelines, assignment rebinding, import aliases, constants, dynamic paths, shadowing, function reachability, prose and metadata decoys, fences, optional effects, and artificial prerequisites. Phase5 does **not** claim that aliasing, mutation, dynamic inputs, optionality, or decoys are new concepts. The new extraction scope is the specified shutil/os primitives and wget/tee/echo/printf forms, with distinct signature, destination, and binding combinations. The 24 cells are API/construction combinations, not 24 unrelated grammatical inventions.

| Split | Families |
| --- | --- |
| Development | copyfile endpoint pair; copy aliases with directory ambiguity; move namespace effects; rmtree targets; os remove/unlink; rename namespace effects; mkdir mode; makedirs existence option |
| Validation | copyfile keyword and constant bindings; copyfile reassignment; dynamic move source; dynamic os deletion; nested filesystem guards; parameterized filesystem helpers; wget output pair; tee multiple outputs/append |
| Heldout | printf quoted metacharacters and redirection; echo descriptors/variables; os import shadowing; shutil member mutation; expanded call arguments; wget expansion/body-option boundary; filename-like directory ambiguity; inert new-API token payloads |

The ontology is logical capability effects, not a syscall trace. `copyfile`/`copy` require a source read and destination write. `move`/`rename` have source namespace deletion and destination namespace write; no unconditional content read is asserted. Directory creation is `file.write`; recursive and ordinary deletion are `file.delete`. This ontology does not assert recursive subpath enumeration or physical execution.

`shutil.copy` and `shutil.move` can accept an existing destination directory. Without visible filesystem evidence, their final destination resource is unknown even if the argument ends in `.txt`. `copyfile` and `os.rename` have different endpoint semantics. A copy/move unknown does not erase its known source capability. No private filesystem metadata is supplied to justify resolution.

Unknown expanded arguments/options remain unsupported, rather than being assigned fabricated effects. A proven pure replacement lambda is a non-action; an unknown shadowing adapter is an uncertainty. Quoted shell payload text is inert. The mkdir mode and imported alias variants remain real source capabilities even if a bounded implementation elects to abstain; an implementation whitelist does not change literal gold. Dynamic bindings, negative samples, and unsupported syntax are preserved in the denominator and reported separately.

## Reasoning contract

The frozen file contains 18 different finite dependency constructions, one case per family, with six families per split. Each case has three matched execution-scope contexts (`allow`, `deny`, `missing`), giving 54 case-context instances. There are 50 scored candidate nodes and 10 unscored support nodes. The same opaque canonical IDs, candidate table, source, inputs, and goal must be used for every graph view and model. Family names, private rationales, private routes, and gold labels must not enter prompts.

Every sample is valid Python syntax with explicit `Path`, `requests`, and `json` imports. Files and network responses are finite specification inputs. Outputs are absent initially unless stated otherwise. No sample was executed and no live requests were issued.

Authorization refers to the selected current execution grant. Scope rules specify exact operations and resources and, where applicable, exact network payload values. The allow context for an unbound output destination is still unknown: an exact grant for `selected.txt` does not bind a runtime path. In historical v1, the deny context universally grants no filesystem/network effects, so denial remains definite even for unbound paths. In active v2, only one selected bound effect is outside its exact grant; other grants remain and unbound destinations remain unknown. Missing scope is distinct from denial.

Implementation necessity is a **finite-intervention estimator** on the displayed source and fixed inputs. Omit one candidate effect, replace the complete value-producing expression containing it with the documented omission value, and preserve other statements. This includes a selected `.text`/`.ok`, JSON parse, or integer conversion. A skipped write/delete has no side effect. Replacement applies to every visit to the selected source site. These bounded interventions are not arbitrary program repairs and are not literal source-line deletion.

Strict-manual ablation validity is recorded separately: would replacing only that statement with `pass` leave current live references and control syntax defined? Removing an assignment used later can be invalid even when the finite intervention has a precise outcome. A valid deletion can also fail the goal. These concepts must never be collapsed.

Task necessity means **finite task-route necessity under fixed capability assumptions**, independent of the paired current execution grant. The public route summary discloses the closed route domain or explicitly states its incompleteness. Private reference routes are scorer witnesses only; full successful effect plans are not in prompts. A necessary but denied effect is an explicit scope conflict. This experiment therefore tests controlled scope reasoning; it does not establish current-authorized feasibility or authorize executing a route. Legal recovery is a separate evaluation.

Candidate identity denotes the scored source capability. A stated replacement may retain that capability while rewiring its input. An incomplete replacement catalog does not guarantee retention of the same scored site merely because an artifact with the same filename remains the goal. No-available-route evidence must not be treated as false, and empty route sets must not produce vacuous truth.

The corpus has 42 source-supported oracle edges: 33 DATA, seven CONDITION, and two CALL. Edges represent syntactic/data-binding associations supported by quoted source spans, not causal certainty. Loop updates, mutable containers, filesystem round trips, and helper returns require the cited intermediate lines. No sequencing edge is invented. This makes graph usefulness an empirical question: the graph can include non-necessary dependencies, while a goal conjunct can require an effect without an edge.

## Unknown reasons and evaluation limits

Every gold unknown contains its dimension, reason, missing evidence, and next safe action. Across 150 node-context records the historical v1 has 50 `missing_scope`, two `dynamic_binding`, six `incomplete_reference_routes`, and six `insufficient_effect_semantics` entries. Active v2 has four `dynamic_binding` entries and the same other counts. Missing-scope counts are deliberately large because scope is paired across every case; aggregate unknown accuracy must therefore be accompanied by per-reason and per-dimension counts.

| Reason | Missing evidence | Next action |
| --- | --- | --- |
| `missing_scope` | Independent operation/resource/payload grant | Obtain exact execution scope. |
| `dynamic_binding` | Concrete runtime resource | Bind the operand and re-check scope. |
| `incomplete_reference_routes` | Closed permitted route catalog or bypass witness | Obtain closure or a concrete successful bypass. |
| `insufficient_effect_semantics` | Opaque return/failure/omission contract | Specify that contract before assessing the intervention. |

Gold unknowns are justified. A model's unknown on a gold yes/no is an avoidable abstention, scored separately. `invalid_strict_ablation` is a diagnostic, not an automatic unknown in the finite estimator. Extraction also records `shadowed_binding`, `unsupported_syntax`, and `ambiguous_destination_kind`; these are extraction evidence states and must not be silently remapped into reasoning labels.

The public task summaries contain concise permitted-route descriptions and closure assumptions because the task cannot be fairly judged without them. They do not enumerate successful plans or give node labels. The node table and source still carry substantial information, so a graph benefit is neither assumed nor guaranteed. Table-only, automatically inferred, oracle, shuffled, and length-control graph views should differ only in the assigned view, with fixed source and candidates. Oracle graph comparison is an upper-bound source-relation intervention, not a claim that a graph reveals causal necessity by itself.

A symbolic reference baseline supplied private finite routes can mechanically check the authored labels. That is a consistency check under the specification, not extraction, autonomous program understanding, natural-language scope interpretation, or an independent accuracy benchmark. It must not be presented as an end-to-end competitor or evidence of general semantic correctness. Model outcomes, new extraction failures, and real-repository frequency claims are outside this document.
