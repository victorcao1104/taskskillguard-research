# v13 → v14：改变了问题的表达，保留了强对照

旧版本在 `../stateful-recovery-v13/`，存档标签为 `archive-before-goal-recovery-v14-20261018`。本轮全部内容另存于本目录；没有替换旧模型回答、旧结果或旧论文。

| 项目 | v13 | v14 | 能作出的判断 |
|---|---|---|---|
| 可信任务 | 直接提供较接近计算流程的查询描述 | 提供输出的数量、覆盖、预算、唯一性等约束，不给过滤/连接/聚合步骤 | 去除了直接计算配方，但精确的有限约束仍可被通用搜索求解 |
| 真值与生成器 | 原始辅助程序与编译器共享部分构造逻辑 | 原始 Skill 辅助程序、强编译器与最终真值检查分别实现 | 降低共享实现带来的循环验证风险；仍不是独立团队构建的基准 |
| 结果复用 | 一次输入上的匹配不足以支持未来输入上的复用 | 每次执行按当前输入、当前目标和具体值重新认证 | 认证当前值，不声称证明任意程序的全局等价性 |
| 新输入验证 | 较少的名义输入检查；已观察到通过后失效 | 18 个构造阶段输入，16 个最终输入，32 个更大输入；冻结后不回填答案 | 补充特定盲区，仍有失败，不能称为形式化证明 |
| 普通修复/重新规划 | 主比较对状态模块的共享不够细 | 同时报告 raw 与 state 版本 | 可把自动状态处理与完整方法的增量分开 |
| 强编译器 | 最强控制，全部可完成任务成功 | 保留来源无关的搜索、状态回执处理与独立检查复用 | 没有为了突出模型方法而削弱对照 |
| 正常任务 | 容易混入恢复阶段比较 | 单列强制重建探针；另审计安全原程序直通 | 重建失败不能当成部署时正常任务误阻率 |
| 不确定效果 | 已发送/未发送/未知状态 | 同时测试未知状态的两个物理世界，模型看不到隐藏答案 | 没有状态查询权限时停止；不把未知当成未发送 |

## 为什么不能直接比较旧版与新版的百分比

v13 和 v14 的任务、可完成案例比例、验证输入、状态实现和模型协议都发生了变化。v13 的 72 次比较中有 60 次设计上可安全完成，v14 则有 63 次。不能把 Luna 完整方法从 v13 的 55 次到 v14 的 63 次，解释成“修复带来 8 次净收益”。这不是同一批案例上的配对干预。

本轮的有效归因来自 **v14 内部**：普通修复是否因加入状态模块改善；完整方法是否超过已共享状态模块的修复与重新规划；取消复用是否改变结果；强编译器是否仍然占优。完整数据、配对差异与家族层面的不确定性见 `reports/analysis.json`。

## 延续与改变的结论

编译器仍然最强，说明“检查目标不给计算配方”只是排除了一个过于直接的捷径，没有让有限领域中的求解本身变难。新结果支持保留强编译器作为核心对照。

完整方法在主实验的被阻断任务中表现较好，也减少模型请求；但与共享状态模块后的普通修复相比，优势很小。在组合条件中 Luna 完整方法的实际完成数少一次，该次原始记录为 API 拒绝请求（HTTP 400 / invalid_prompt），不是已生成程序执行失败。它保留在观测完成率中，但不能作为算法较差的证据。结果复用的完成率消融为 Luna 0 次、Mini 1 次差异，不能证明它是总体成功的主要原因。

本轮更清楚地区分了两个风险：复用未经检查的旧值，以及新程序在新输入上过度约束任务。前者有直接构造的反例支持修复价值；后者仍在 Mini 的 7 个已接受程序中出现，全部记录保留。

这里的“独立价值”证据仍然有限。可以讨论固定权限下的状态管理、验证不足和修复何时值得使用，不能写成一个已普遍超过编译、修复和重新规划的新方法。
