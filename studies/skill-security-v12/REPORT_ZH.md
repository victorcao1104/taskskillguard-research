# 回到 Skill 安全：第五轮方案与第六轮验证方法的整合

这轮论文的研究对象重新明确为：**第三方 Skill 请求执行的行为，是否超过用户任务的授权；在阻止越权后，能否通过合法路径完成任务。** 后期关于查询选择和停止条件的研究不再承担论文主线。第五轮提供原有的任务条件检查、数据流约束和合法恢复框架；第六轮提供可执行真值和能力相同的强对照。旧结果全部保留。

## 这次与 Skill 的联系是什么

每个新样本都是一个合成 Skill 包，包含 `SKILL.md` 和实际的辅助脚本文本。系统从包内调用指令选择脚本，再把受支持的代码转换为有限执行模型。每个效果都指回原始文件、行号和文件校验值。修改脚本会改变被分析和执行的行为。因此，包内容实际影响实验，不只是给一个抽象任务套上 Skill 名称。

但支持范围很小。我们没有执行任意 Python，也没有接入真实文件系统或网络工具。样本覆盖的是具体安全机制，不能代表真实 Skill 平台的攻击分布。原始数据集没有用于本轮实验，也没有新增人工标注。

## 最值得写进论文的发现

**第一，检查操作和目的地还不够，必须检查数据来源。** 无故障的 24 个攻击样本中，14 个产生越权操作，另 10 个把受限制的数据发到本来允许的目的地。单独的权限检查挡住前 14 个，但挡不住后 10 个。加入数据来源传播与发送限制后，两类违规都被阻止。合法样本的 24 个任务仍全部完成。

这支持一个具体思想：对 Skill 的权限控制不能只问“是否允许调用发送工具、是否允许这个地址”，还要问“这次发送的内容是否允许离开它的来源”。它没有证明一种全新的信息流理论，而是展示了这些机制在 Skill 包、用户任务和辅助脚本之间怎样结合，以及每一层具体解决了什么。

**第二，某个危险行为是原脚本的前置条件，不等于用户授权它。** 人为前置条件样本让原程序依赖一次越权读取。删掉读取会使原程序失败，但合法替代脚本能完成相同任务。这说明“当前实现需要”和“任务允许”必须分别判断。

本轮还发现一个容易误读的指标：目录必要性按“操作—资源类别”比较。例如，合法任务需要向指定地址发送报告，所以这个发送类别可能是必要的；这不能证明发送秘密内容也是必要的。论文会明确说明这一点，避免用必要性为恶意内容辩护。

**第三，合法恢复确实有用，但收益主要来自合法替代路径及运行时检查。** 无故障时，单独的权限与数据流检查会停止所有被攻击的原路径；加入预先给定的合法替代脚本后，24 个受攻击任务全部完成。但“全部禁止原路径，再恢复”也能完成全部 48 个正常与攻击任务，因此不能把恢复后的成功归功于模型准确理解了 Skill。

**第四，复杂选择策略的收益很有限。** 两种恢复方法都能查看相同候选脚本、状态、权限和剩余额度，并模拟所有候选。它们在 1,344 组配对条件中的完成结果完全相同。普通额度下，两者都完成 140/192 个条件；按调用数选择用了 680 次调用，按固定顺序选择用了 822 次。这里能支持的是特定候选顺序下的成本节省，不能写成更高的安全性或完成率。

## 模型和图的结果为什么不能夸大

新模型实验有 288 个条件，但只有 264 个不同请求，因为部分合法样本的输入完全相同。286 个条件取得符合协议的答案，另外两个保留了接口的 HTTP 400 `invalid_prompt` 失败，没有自动重试。重复条件不能被当成新的独立回答。

权限标签通常较好，但对必要性和 unknown 的理解不稳定。普通样本的目录类别必要性中，Luna 的源文本视图仅正确 54/180，mini 正确 157/180。Luna 有 113 次把真值为 yes 的类别答成 no；原始回答没有足够解释来证明它内部为什么这样判断，论文不会编造原因。

数据流准确率只在真正的发送点上计算：普通样本有 52 个发送位置，不能把其余 128 个“不适用”位置混进分母制造高准确率。源文本与图视图中，Luna 分别正确 39/52 和 41/52，mini 分别正确 38/52 和 39/52。这些局部变化没有形成稳定的端到端收益，图也没有在所有标签上普遍改善。

本轮图条件额外增加了文本长度，没有新的等长填充或重复采样对照，所以只能讨论“加入这份图信息”的效果。第五轮更严格的图对照负面结果继续保留，不会用本轮局部增长覆盖它。

## unknown 和可用性损失还剩什么

unknown 至少有三种不同来源：静态位置在该任务中未执行；原路径本身未达到目标，因此无法用简单删除实验判断必要性；给定目录没有合法解，无法形成任务必要性的结论。这些不能统称为模型失败。模型还会额外对已有确定真值的项目回答 unknown，也会对应该 unknown 的项目作出肯定判断。

空的开放目录与空的封闭目录在本轮攻击上下文中都没有合法列举路径，所以两组的 52 个位置都得到目录 unknown。这不能证明目录是否封闭带来了收益。这个实验设计的辨别能力不足，会在论文中明确指出。

预检造成的可用性损失有一个清晰例子：同一行循环发送两次，第一次合法，第二次超过次数限制。模型给整行打标签，若整行禁止，就连第一次合法发送也被挡住。运行时检查可以逐次判断，先允许第一次，再阻止第二次。由于本实验规定拒绝尝试也消耗次数额度，模型预检还可能耗掉恢复所需的唯一机会。这是“整行标签过粗”和“保守计费规则”共同造成的损失，不应泛化为所有预检都必然有害。

## 结果的可靠性与修订记录

首次独立对照的 324 项检查中有 292 项不同。288 项是读取日志中的 value 字段，一个表示请求参数，另一个表示返回内容；另 4 项涉及缺失文件读取。修订参考解释器后，324 项全部一致。两项当前必要性标签也从 yes 改为 no。所有原始记录、原参考代码和修订说明均保留，不能写成首次就全部通过。

旧提取器的定位统计也有一次计分错误：读取了错误层级的行号字段。修正后的宽松位置覆盖为 134/180，按操作类型匹配为 128/180。新适配器在受限语法内找到 180/180 个位置，但旧提取器面向更广的实际工具，而新样本使用自定义模拟发送接口，二者不是公平的通用能力竞赛。

7 个禁用网络、无宿主挂载、只读根目录、非特权用户的容器复现了全部 6,720 个编译后执行条件。离线重放还核对了全部模型回答后的 3,456 个执行条件，不需要付费调用。这些验证支持结果可复查，但不能代替真实服务语义、无限程序分析或独立人工安全审计。

## 这篇论文可以诚实主张什么

最后的独立代码审查还给出了一个新的负面反例：秘密值控制是否删除公共文件，然后脚本读取该公共文件并发送结果。一个世界发送空字符串，另一个发送原有内容，而当前检查都放行。这通过文件的存在或缺失泄露了信息，说明即使在支持的语法内，当前数据流跟踪也不完整。该反例作为独立的审查后探针保存，未混入原来的 48 个样本，也没有在本版中修复。因此，“24 个攻击样本全部被挡住”不能改写成“所有受支持程序都安全”。

可以主张：一个围绕 Skill 包和用户任务的、可复现的有限安全实验；清楚区分操作权限、数据流权限和必要性；证明这组机制下仅检查目的地不够；展示合法恢复的收益及其对可信替代路径的依赖；给出能力相同的对照，说明复杂选择、模型预检和图表示的贡献边界。

不能主张：已解决真实 Skill 生态安全；能自动生成可靠授权；优于完整的 SkillScope、Progent 或 CaMeL；能抵抗自适应攻击；或者图和模型已经稳定超过强确定性方法。这些方法是研究启发与相关工作，并非本轮复现的外部基线。

下一步若继续纯合成研究，应优先扩大有实质差别的任务和组合结构，按每次效果而非整行提供预检决定，分离本地拒绝和真实工具调用额度，并加入含合法规避证据的开放目录条件。不要再通过增加查询策略把主线转回通用代理规划。
